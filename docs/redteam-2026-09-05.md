## 1. Deponent (gate-only mode, `use_jail=False`)

Held (all `BLOCK`): `python3 -c` with `chr()` obfuscation, `/usr/bin/python3`,
`Python3`/`PY.EXE` case variants, `echo; python3` chaining, `env python3`,
`xargs python3 <`, `PYTHON=python3 sh -c`, `cat /etc/passwd`,
`cat ../../../etc/passwd`, `sort /etc/passwd`, `grep -f/etc/passwd`,
`rm -rf .`, `rm<TAB>-rf .` (falls through deny-substring but `rm` is not
allowlisted → still blocked). Chaining returns `chain-unjailed`;
interpreters return `interpreter-unjailed`.

### D-1 — BREAK, NEW, **High**: out-of-sandbox write via flag-glued path

```
$ .venv/bin/python dep_probe3.py
ALLOW  [bounded-local-exec] sort -o/tmp/DEPONENT_ESCAPE_15405 data.txt
  target written outside sandbox?: True 'SECRET-EXFIL-LINE\n'
BLOCK  [arg-path-escape   ] sort -o /tmp/DEPONENT_ESCAPE_15405 data.txt
```

Root cause, `deponent/gate.py::_evaluate_cmd`:

```python
for t in toks[1:]:
    if t.startswith("-"):
        continue                      # <- glued "-o/tmp/x" never reaches _in_sandbox
    if "/" in t or t in (".", ".."):
        if not self._in_sandbox(t): return BLOCK("arg-path-escape")
```

Any allowlisted program with a `-oFILE`/`-fFILE`-style option is a write or
read primitive to any path not caught by the substring denylist (`/tmp/`,
`$HOME`-relative absolute paths, other users' dirs are all not denied).
`sort` is in `GATE_ONLY_SAFE_HEADS`, so this works in the exact mode that was
hardened yesterday as "deny-by-default". Confirmed the same command with
`use_jail=True` on this Linux box fails at the OS layer (`exit=2 …
Permission denied`), so Seatbelt/jail users are protected; gate-only users
are not. Also confirmed `grep -f/tmp/<file> data.txt` is ALLOWed (reads an
out-of-sandbox file as a pattern list; content leaks via match/exit code).
Passing `allow_unjailed_heads={"sort"}` does not change the outcome.

Fix: apply `_in_sandbox` to the path component of any token that contains
`/` regardless of a leading `-` (split on the first `/`, or on `=` for
`--output=/…`); add a regression test with `-o/tmp/x`, `--output=/tmp/x`,
`-f/etc/hosts`. This qualifies as the "new independently verified security
finding" that AGENTS.md requires before editing `gate.py`.

Not tested: ledger tamper (deponent's refusal ledger integrity), symlink
inside sandbox pointing outside (would need a write primitive first — D-1
provides one).

## 2. Fleet Watch (`fleet guard --json`, session leases)

Held: DB `BEGIN EXCLUSIVE` held 14 s → `allowed:false, guard_error_fail_closed:
OperationalError: database is locked`; corrupt `registry.db` → deny; `~/.fleet-watch`
is a file → deny; read-only dir → deny; exclusive lease by live PID → deny;
symlink / `./` / `sub/..` aliases of a locked repo → deny (paths are
`resolve()`d); owner dead → released; live PID with mismatched create-time
(PID reuse) → released; NULL create-time (pre-migration) → block; ownerless
exclusive with fresh heartbeat → block; unparsable heartbeat → fail-closed
`ValueError`; future heartbeat (clock skew) → block; exclusive + ancient
heartbeat → block; cooperative + ancient heartbeat → lapses (documented);
`ps` missing from PATH → block; lease owned by PID 1 (PermissionError) →
block; `--write-scope /etc/passwd` and `../../etc` → fail-closed
`ValueError`; 100 kB `--session-id` → structured deny. Every error path
returned structured JSON with `allowed:false`; no crash observed.

### F-1 — BREAK, NEW, **High**: exclusive repo lease is not mutually exclusive under contention

```
$ .venv/bin/python redteam/fw_race.py     # 16 concurrent `fleet session start --exclusive-repo-lock` on one repo
trial 0: exit0=4/16  ACTIVE exclusive rows for repo: 4 -> ['t0-8','t0-1','t0-0','t0-3']
trial 1: exit0=6/16  ACTIVE exclusive rows for repo: 6
trial 2: exit0=5/16  ACTIVE exclusive rows for repo: 5
```

Root cause, `cli.py::session_start`: `referee.preflight_register(conn, …)`
(read) and `registry.upsert_session_lease(conn, …)` (write) run as separate
autocommit statements with several `ps` subprocess calls in between
(`_inspect_process`, `_pid_create_time`). There is no `BEGIN IMMEDIATE`
around check+insert and no partial unique index on
`session_leases(repo_dir) WHERE status='ACTIVE' AND repo_lock_mode='exclusive'`.
This directly violates the "two writers" invariant that the create-time and
fencing-epoch work exists to prevent. Fix: wrap preflight+upsert in
`BEGIN IMMEDIATE … COMMIT` (SQLite serialises writers, so the second
transaction re-runs preflight and sees the first lease), and add the partial
unique index as a belt-and-braces constraint; add a test that spawns N
concurrent starts and asserts exactly one ACTIVE exclusive row.

### F-2 — weakness, NEW, Medium: repo identity is exact-path, not repo-root

`guard --repo <locked>/subdir` → `allowed:true, repo available` while
`<locked>` is exclusively held. Any agent that guards a sub-path (or the
git worktree, or `src/`) bypasses the lock. Fix: canonicalise to
`git rev-parse --show-toplevel` when inside a git repo, or deny when the
requested path is inside (or contains) a locked repo_dir.

### F-3 — same-user trust boundary, DOCUMENTED-ish, Low

`--session-id victim` or `FLEET_SESSION_ID=victim` → `owned by current
session`; and a `ps` shim on PATH that prints a wrong create-time releases a
live owner's exclusive lease (`allowed:true`). Both require running as the
same user that owns `~/.fleet-watch`, which is the documented cooperative
model; recorded so nobody reads "exclusive" as a security boundary.

### F-4 — weakness, Low: `--gpu -5` → `allowed:true`

Negative budgets are trivially satisfied; should be a usage error.

Also noted: `preflight_register` output text says `DENY: … locked by
exclusive session race-6` — correct when it fires; the problem is only that it
races.

## 3. Sworn (evidence log + staged-path gate)

empty log (`EMPTY`, exit 1), duplicate-key/CRLF/unicode/key-order canonical
probes. BREAK (all DOCUMENTED — an unsigned hash chain proves only internal
consistency): tail truncation (`Chain: VALID, 2 entries`), full re-chain
after edit, single-genesis replacement, forged append with valid `prev_hash`.

Signed log — HELD: re-chain without the key (`signature verification
failed`), stripped/blanked signatures (`missing signature in signed log`).
BREAK: tail truncation still `VALID` (DOCUMENTED); **repo-controlled key
swap** — replace `.sworn/keys/*.pub`, rewrite `key_id`, re-chain, re-sign
→ `VALID`. Public key is resolved from the repo it protects, so a repo writer
can re-root trust. DOCUMENTED as a boundary, but this is the single change
that would make `sworn verify` mean something to a third party: accept
`--expected-pubkey`/`--expected-key-id` and fail closed when absent in CI.

### S-1 — BREAK, NEW, Medium: staged-path security gate bypasses

```
[symlink_to_sensitive_target]      check_exit=0  SWORN PASS   # staged `safe-link` -> crypto/vault.key
[unicode_homoglyph_directory]      check_exit=0  SWORN PASS   # seсrets/token.txt (Cyrillic с)
[git_add_N_explicit]               check_exit=0  ''           # git add -N secrets/ita.txt: not in --diff-filter=ACMR
[dotdot_sensitive_path]            check_exit=1  SWORN BLOCKED # held
```

The gate matches regexes against staged pathnames only. Fixes: resolve
symlinks and test the target path; NFKC-normalise + confusable-fold before
matching; include intent-to-add entries (`git diff --cached --name-only
--diff-filter=ACMRTUXB` or `git ls-files --others --exclude-standard` for
`-N`). Content-based probes (binary blob containing `PRIVATE KEY`, split-line
secret, base64 key) all PASS — the gate never claimed content scanning, so
those are out of scope, but the README should say "path patterns only" in
the first paragraph.
